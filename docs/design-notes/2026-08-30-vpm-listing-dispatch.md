# 設計ノート: VPMリスティングへのリリース通知(repository_dispatch)

- 日付: 2026-08-30 / ステータス: 採用済み(UITKFontFix側のみ実装。リスティング側は別リポジトリ作業)
- 発端: 0.2.0 / 0.3.0 のリリース後、VPMリスティング(`c-colloid/vpm`)の
  `index.json` に新バージョンが数時間反映されなかった

## 根本原因

リスティング側の収集ワークフローは `push` / `workflow_dispatch` / `schedule`
(6時間毎)でしか起動しない。リリースは UITKFontFix 側で起こる出来事であり、
リスティング側には何の入力も届かないため、**反映遅延の上限は cron 間隔と等しい**。
さらに cron を毎時0分に置くと GitHub Actions の混雑スロットに当たり、
実行が数時間遅延またはスキップされる(今回 06:00 の回が3時間以上到着しなかった
のがこれに該当)。つまり遅延は不具合ではなく、押し出し側の通知が存在しない
という設計上の欠落。

## 選択肢

| 案 | 内容 | 判定 | 根拠 |
|---|---|---|---|
| A | cron間隔を短縮(例: 毎時) | 棄却 | 遅延の上限を縮めるだけで押し出しにならない。無風時も毎時実行し続ける浪費。混雑スロット問題も解決しない |
| B | リリースジョブから `repository_dispatch` を送り、cron は予備として残す | **採用** | リリース確定を唯一の起点にできる。通知経路が落ちても cron が最終的に拾う二重化 |
| C | リスティング側から各パッケージリポジトリをポーリング | 棄却 | 実質Aと同じ。リポジトリが増えるほどAPI消費が増える |
| D | リスティング側リポジトリへ直接 commit / PR を作る | 棄却 | 生成物の作り方をリスティング側から奪う。トークン権限も広くなる |

B の副作用として、リスティング側の cron は0分から外す(混雑回避)。これは
B が無くても有効な緩和だが、B と同時に入れることで「即時経路+ずらした予備」に
なる。

## 通知が失敗しても壊れない設計

通知はリリースの付随処理であり、リリースの成立条件ではない。したがって:

- `continue-on-error: true` を付け、PAT期限切れ・権限変更・APIエラーでも
  リリースジョブは成功のまま終わる(その回は cron が拾う)
- トークン未登録(secret が空)の場合はAPIを叩かず `::warning::` を出して正常終了する。
  認証エラーのログではなく「未設定」と読める形にして、期限切れとの区別を付ける

## 発火条件をステップ出力にした理由

当初案は `if: steps.release.outcome == 'success'` だった。しかしリリース作成
ステップは「タグ既存かつアセット済み = 何もしない」経路でも `exit 0` するため、
`outcome` では**リリースが起きなかった回にも通知が飛ぶ**。再生成は冪等なので
実害は無いが、リスティング側の実行ログが無意味な起動で埋まり、本当の起点が
追えなくなる。そこでリリース作成ステップに `id: release` と
`released` / `version` の出力を持たせ、実際に変化があった経路
(新規リリース作成・既存タグへのアセット追補)だけ `released=true` を書く。

アセット追補も `true` に含める。リスティングは zip と package.json の
添付を前提に収集するため、追補された時点で初めて収集可能になるから。

## 順序の保証

`gh release create` はアセットのアップロードまで終えてから戻る。通知ステップを
その**後段の別ステップ**に置くことで、リスティングが読みに来た時点で
アセットが揃っていることが保証される。

## トークン

`GITHUB_TOKEN` は他リポジトリへイベントを送れないため、リスティング側の
Contents 書き込み権限だけを持つ fine-grained PAT をリポジトリシークレット
`VPM_DISPATCH_TOKEN` に登録する。スコープをリスティング1リポジトリの
Contents に絞ることで、漏洩時の影響範囲を限定する。
`POST /repos/{owner}/{repo}/dispatches` の認可にはこれで足りる(公式RESTドキュメントで確認)。

## 検証結果(2026-08-30、両経路とも実ランナーで確認)

静的検証は actionlint 1.7.7 + shellcheck 0.10.0 グリーン。実行時は両経路を確認:

- **不発側**(run #15 / version 0.3.0): タグ・アセットとも既存のため
  リリースステップが `released=false` を書き、通知ステップが `skipped`。
  意図しないリリース回で通知が飛ばないことを確認
- **発火側**(run #16 / version 0.4.0): リリース `v0.4.0` 作成後に通知ステップが実行。
  ログ上 `::warning::`(トークン未設定ガード)も `gh api` のエラーも無し
  = 204 No Content。直後にリスティングの公開 `index.json` へ 0.4.0 が反映され、
  リリース→通知→再生成の全経路が繋がった

### 検証時の注意: ステップの conclusion は成功判定に使えない

`continue-on-error: true` を付けたステップは、失敗しても Actions API 上の
conclusion が `success` になる(continue-on-error 適用後の値が入るため)。
さらに本ステップはトークン未設定時も警告を出して `exit 0` する。したがって
通知が実際に届いたかは **ステップの成否ではなくログ本文**(警告の有無・
`gh api` のエラー出力の有無)で確認すること。

## 残存リスク

- GitHub API の read-after-write 整合の揺らぎで、通知直後の収集が新リリースを
  取りこぼす可能性は理論上残る。固定 sleep のような当て推量の緩和は入れず、
  cron の予備経路に委ねる
- リスティング側(`repository_dispatch` トリガー追加と cron のずらし)は
  別リポジトリのため本コミットには含まれない。導入済みであることは
  当該リポジトリの build-listing ワークフローで確認した
  (`types: [package-released]` / `cron: "23 */6 * * *"`)。
  片側だけの状態では通知はエラーにならず単に無視される(安全側)
